# RQ5 category coding: instructions

How the fixture guidance found in agent guidance files is categorized. This
covers the second coding step of RQ5. The first step decided, for each
repository with a fixture keyword match, whether its guidance is about test
fixtures (`decision` in `rq5_repository_coding_sheet.csv`, see `README.md`).
This step describes *what* that guidance says, using categories built by this
study (not the themes of Ardic et al.).

## Files

| File | Role | Who writes it |
|---|---|---|
| `rq5_category_sample.csv` | The coding sheet: all repositories coded `yes`, in random order, with their matched lines | Generated once; coders fill the coding columns |
| `rq5_category_codebook.yaml` | The categories: `code`, `name`, `definition` | Coders |
| `rq5_agreement_sheet.csv` | 20 coded repositories for a second coder (optional) | Generated; the second coder fills `categories` |
| `rq5_snippets.md` | The full matched lines with two lines of context and GitHub links, one section per row of the repository coding sheet | Generated by the scan |
| `../rq5_coding.md` | The results | Generated by `rq5_coding` |

The repository coding sheet is never written by this step: the sample is read
from it.

## Sampling design

- **Population:** the 556 repositories coded `yes`.
- **Order:** one simple random permutation of the repositories in the coding
  sheet's order, with seed **20261012**. Not stratified.
- **Checkpoints:** Cochran's sample size at 95% confidence, p = 0.5, with the
  finite population correction, rounded up:

  | Margin of error | n0 = z² p (1 − p) / e² | n = n0 / (1 + (n0 − 1) / N) | Checkpoint |
  |---|---|---|---|
  | 10% | 96.04 | 82.02 | **83** |
  | 5% | 384.16 | 227.43 | **228** |

  The `checkpoint` column of the sample says which checkpoint a row belongs
  to: `83` for rows 1 to 83, `228` for rows 84 to 228, empty after.
- **Margin of error reported:** z · √(p (1 − p) / n · (N − n) / (N − 1)) for the
  sample size actually reached: 9.9% at 83, 5.0% at 228.

The seed, the population and the checkpoints are constants in
`collection/rq5_category_sample.py`; generating the sample fails if the
population is not 556 or the checkpoints are not 83 and 228.

## The coding sheet

`rq5_category_sample.csv`, one row per repository:

| Column | Content |
|---|---|
| `sample_order` | 1 to 556, the random order. Code in this order. |
| `checkpoint` | `83`, `228` or empty |
| `repository`, `primary_language` | From the repository coding sheet |
| `snippets` | Every fixture match of the repository: `[row id] path:line (terms)`, the line before, the matched line (marked `>`) and the line after. Row ids are rows of `rq5_fixture_matches.csv`. |
| `open_code` | **To fill:** free text describing what the guidance says |
| `categories` | **To fill:** final category codes, separated by `;` |
| `notes` | **To fill (optional):** free text |

A cell holds at most 32,767 characters. A repository with more matched text
shows the lines that fit and ends with
`[N more matched lines not shown: see section X of rq5_snippets.md]`; read the
rest in that section.

## How to code

### Unit and evidence

- **Unit:** the repository. Its categories describe the fixture guidance of all
  of its guidance files together.
- **Evidence:** the matched lines and the lines around them, as in the first
  coding step. Use `rq5_snippets.md` when the cell's one line of context is not
  enough. Do not look elsewhere in the repository and do not rely on
  specialist knowledge of the project.
- **Scope:** categorize only what the guidance says about test fixtures. A
  matched line that is not about fixtures (the repository is `yes` because of
  another line) adds no category.
- Every repository in the sample was coded `yes`, so each gets at least one
  category. If a repository looks like it should not have been `yes`, write it
  in `notes` and give it the category that fits best; do not change the
  repository coding sheet from here.

### Order: always code from the top

Code rows strictly in `sample_order`, starting at 1, without skipping. The
coded sample is the **prefix** of rows whose `categories` is filled: the
analysis stops at the first row with an empty `categories`. A filled row after
an empty one is an error ("coding out of order"), because it would make the
sample non-random.

Stop at a checkpoint: 83 for a ±10% margin of error, 228 for ±5%. Stopping
elsewhere is allowed, but the report warns and uses the actual size.

### Open coding, then categories

1. **Open code.** For each row, write in `open_code` what the fixture guidance
   says, in your own words: where fixtures live, how they are scoped, how they
   are cleaned up, what they may contain, what not to do with them, and so on.
   Stay close to the text.
2. **Build the categories.** After a first batch of rows, group similar open
   codes into categories. Give each one an entry in `rq5_category_codebook.yaml`:

   ```yaml
   categories:
     - code: fixture_location
       name: Fixture location
       definition: Says where fixtures or fixture files live or must be placed.
   ```

   - `code`: one word in snake_case (letters, digits, underscores); this is the
     value written in `categories`.
   - `name`: a short display name, shown in the results.
   - `definition`: what a repository's guidance must say to get the category.
     Write it so that a second coder can apply it without asking.
3. **Assign categories.** Fill `categories` with every code that applies,
   separated by `;` (for example `fixture_location; cleanup`). A repository can
   have several categories.
4. **Keep the codebook and the coding consistent.** When a category is added,
   split, merged or redefined, go back over the rows already coded and update
   their `categories`. Every code used in the sheet must exist in the codebook;
   the analysis fails otherwise.
5. Continue down the sheet until a checkpoint.

The example entry above only shows the format; the codebook starts empty and
the categories come from the data.

## Commands

```bash
# Once: write the sample and an empty codebook (refuses to overwrite a coded sample)
python -m collection.rq5_category_sample sample

# Results, at any point: decisions plus the categories of the coded prefix
python -m collection.research_questions.rq5_coding

# Optional, after coding: agreement with a second coder
python -m collection.rq5_category_sample agreement-sheet
python -m collection.rq5_category_sample agreement
```

`rq5_coding` writes `research-questions/rq5_coding.md`. It fails, with the rows
involved, if coding is out of order, if a code is not in the codebook, or if
the sample no longer matches the repositories coded `yes` (the repository
coding sheet changed after sampling).

## What the results report

In the "Categories" section of `rq5_coding.md`:

- **Sampling:** population (556), seed, checkpoint reached, sample size,
  confidence (95%) and margin of error.
- **Categories:** name, definition, number of repositories and percentage of
  the coded sample. A repository can belong to several categories, so
  percentages do not add up to 100%.
- **Categories per repository:** median, minimum and maximum.
- **Languages:** the coded sample next to all 556 repositories coded `yes`.
- **Agreement:** once the second coding is complete (see below).

## Inter-coder agreement (optional)

1. When the coded prefix has at least 20 repositories, run
   `python -m collection.rq5_category_sample agreement-sheet`. It draws 20
   repositories from the coded prefix at random (seed **20261013**) and writes
   `rq5_agreement_sheet.csv`: the same snippets and an empty `categories`
   column. It refuses to overwrite a sheet that holds coding.
2. The second coder fills `categories` for all 20 rows using only the codebook,
   without seeing the first coding.
3. Run `python -m collection.rq5_category_sample agreement`, or regenerate
   `rq5_coding.md`, which adds the agreement table once all 20 rows are coded.

For each category, each repository counts as yes or no for that category in
each coding. The report gives, per category, the percent agreement and
Cohen's kappa, and their averages. Kappa is undefined (`n/a`) when both coders
gave every repository the same value for a category; such categories are left
out of the average kappa.

## Do not

- Do not regenerate the sample after coding has started (the command refuses).
- Do not reorder, delete or skip rows of the sample.
- Do not change decisions in the repository coding sheet after sampling: the
  analysis then fails because the sample no longer matches the `yes`
  repositories.
- Do not use a code in `categories` before adding it to the codebook.
