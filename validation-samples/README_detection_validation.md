# Detector Precision Validation Samples

Three Cochran-sized (95% confidence, 5% margin of error), stratified,
precision-only samples for manual single-rater review. The first two are
generated by `python -m collection.detection_validation_sampling`; the
third by `python -m collection.unittest_heuristic_validation_sampling`
(a standalone module -- see its docstring for why). Both reuse
`collection/validation_sampling.py`'s Cochran formula and stratified
allocation -- see that module's docstring for the math.

| File | Population | Stratified by |
|---|---|---|
| `mock-detection/mock_detection_sample.csv` | Fixtures with `num_mocks > 0` (A+C, all 4 languages) | language |
| `pytest-lifecycle/pytest_lifecycle_sample.csv` | Python `pytest_decorator` fixtures classified setup/teardown/setup_and_teardown (A+C) | lifecycle kind |
| `unittest-heuristic/unittest_heuristic_sample.csv` | Python `unittest_setup` fixtures detected by name alone (setUp/tearDown/setUpClass/tearDownClass/setUpModule/tearDownModule), no inheritance check (A+C) | dataset |

Mock-type (dummy/stub/spy/fake/mock category) classification was dropped
from manual validation entirely -- not sampled, reviewed, or reported
here anymore.

**Detector fix, 2026-09-15:** manual review of the unittest-heuristic
sample found `setUpModule`/`tearDownModule` matched by name regardless of
AST nesting -- unittest only ever calls these as plain module-level
functions, never as class methods, but the detector had no nesting check.
2 sampled rows were a confirmed false positive of this kind (both
`Lib/unittest/test/test_setups.py`, vendored into `oils-for-unix/oils` and
`oracle/graalpython`: `class Module(object): def setUpModule(self): ...`,
a fixture used to test unittest's *own* setUpModule mechanism, never
itself invoked as a real hook). Fixed in `detector_python.py` via
`_is_nested_in_class()` -- a same-named method nested in a class is no
longer detected as `unittest_setup`. Those 2 rows (`C:python:42196`,
`C:python:24847`) were removed from `unittest_heuristic_sample.csv`
(380 -> 378 rows) rather than kept as stale FPs against a since-fixed
detector; `precision_report.md` reflects the 378-row sample. This is the
only label change made to any sample after initial review -- everything
else in all three CSVs reflects the original single-pass manual rating.

## Columns

| Column | Meaning |
|---|---|
| `id` | `<dataset>:<language>:<db row id>` -- unique, links back to db/{a,c}.db |
| `source_url` | GitHub blob URL to the fixture's file at its exact commit, line-anchored |
| `raw_snippet` | The code the rater should judge (the fixture body) |
| `detected_label` | What the detector actually assigned |
| `rater_label` | Empty -- filled in by the (single) rater: TP / FP / Unsure / 404 |
| `notes` | Empty -- observations: what was found, edge cases worth a second look, anything that doesn't fit cleanly into one of the four labels |

## Label values

Same convention as `validation-samples/README.md`: **TP** (detection
correct), **FP** (detection wrong), **Unsure** (can't tell from the
evidence shown), **404** (artifact no longer accessible -- excluded from
the precision denominator, not counted as FP).

Precision-only: these samples check whether a positive detection is
correct, not whether the detector missed anything (no recall sampling).

Population: `db/a.db` + `db/c.db` (both full, not `db/c_sampled.db`).
